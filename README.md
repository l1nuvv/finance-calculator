# Контур 2.0

Финансовый планировщик для двоих: один общий бюджет, отдельный вход по логину и паролю, одинаковые операции и остаток на всех устройствах. Интерфейс размещается на GitHub Pages, приватные данные — в Supabase.

## Использование

1. Откройте сайт и раздел «Данные и настройки».
2. Войдите под своим логином и паролем. Настоящий почтовый адрес не нужен.
3. Если аккаунты уже связаны администратором, общий бюджет откроется автоматически. Иначе первый участник создаёт бюджет и передаёт одноразовый код второму, который выбирает «Подключиться».
4. Задайте начальный остаток и дату, добавьте доходы, расходы и повторяющиеся платежи.
5. Проверьте статус «Общий бюджет · синхронизирован» перед закрытием вкладки. Изменения видны на других устройствах в течение 10 секунд, при возвращении во вкладку или по кнопке синхронизации.
6. JSON-экспорт — отдельная резервная копия. Импорт и очистка меняют открытый бюджет, включая общий.

Правки без сети сохраняются в браузере открытого приложения. После восстановления сети они отправляются автоматически. При одновременном изменении разных операций правки объединяются. Если одна операция изменена по-разному или удалена на одном устройстве и отредактирована на другом, нужно выбрать версию в настройках. Дата и начальный остаток разрешаются вместе. При выходе из аккаунта открывается отдельный локальный бюджет.

У новых облачных операций показан логин автора: в списке, ближайших событиях и календаре. Сервер назначает автора по аккаунту и сохраняет его при редактировании другим участником. Для старых и локальных операций без записанного автора показано «Автор не указан». Автор новых импортированных записей — участник, загрузивший их в облако. Поиск операций учитывает логин автора.

В версии 2.1:

- Подсказки «?» открываются наведением, фокусом клавиатуры или нажатием на телефоне. Раздел «Помощь» объясняет сценарии, надёжность, чекбоксы, план/факт, резерв, историю, синхронизацию и установку с примерами.

- «История изменений» показывает последние 100 сохранённых правок, автора, время и значения до/после. В облаке история ведётся сервером, начиная с установки обновления. Отмена проверяет текущую версию операции и не перезаписывает последующие правки. Локальная история хранится отдельно на устройстве; облачная история не включается в JSON-копию бюджета.
- «Факт» у операции задаёт сумму и дату отдельного платежа, включая повторения. Он заменяет соответствующее плановое повторение, а не добавляется второй раз. Если факт включён в исходный остаток, его дата должна быть раньше даты отсчёта. Старую отметку «Вся операция уже учтена» используйте только для исключения всей серии.
- «Обязательные платежи» резервирует расходы и возвраты долга до основного дохода включительно; без указанного дохода — на 30 дней. Признаки обязательности и основного дохода меняются в форме операции. Остаток на сегодня вычисляется из начального остатка и известных событий; неотмеченные события прошлых дней считаются по плану.
- Светлая/тёмная тема сохраняется отдельно на каждом устройстве; при первом открытии учитывается тема системы.
- Приложение устанавливается на главный экран через меню браузера. Для нового входа и истории нужна сеть. После загрузки интерфейс доступен офлайн, а открытая сессия использует свою локальную облачную копию. Фоновая синхронизация при закрытом приложении не выполняется: откройте его при подключении к сети. Service worker кэширует только публичные файлы интерфейса, без запросов авторизации и бюджета.

Сессия живёт в текущей вкладке; после закрытия браузера может понадобиться повторный вход. Локальные копии не шифруются и доступны владельцу профиля браузера. Сайт не предназначен для использования на общем компьютере без доверия к этому профилю.

## Локальная разработка

Нужен Node.js 22 или новее. У приложения нет сторонних зависимостей и внешних CDN.

```sh
node scripts/serve.cjs
# http://127.0.0.1:8765
node test.js
node test-sync.cjs
node test-controller.cjs
node scripts/check-public.cjs
```

`npm test` запускает все эти проверки; `npm run build` подготавливает только публичные файлы в `_site/`. ZIP-архивы не нужны.

## Развёртывание

- В GitHub Settings → Pages выберите GitHub Actions. Workflow `.github/workflows/pages.yml` проверяет проект и публикует его при обновлении `main`.
- В Supabase SQL Editor примените `supabase/schema.sql`. Проверки `supabase/security-tests.sql` создают временные данные и откатывают их целиком.
- В `config.js` разрешены только URL проекта и **publishable key**. Secret key, service_role, пароли, JWT и резервные копии не должны попадать в исходники.
- В Authentication → Users → Add user → Create new user создайте два аккаунта. Внутренний идентификатор состоит из выбранного логина, символа @ и домена `users.kontur.invalid`. Включите Auto confirm user. В приложении нужен только логин, без домена.
- Логин: 3–32 латинские буквы, цифры, `_` или `-`, регистр не учитывается. Создавайте внутренний идентификатор в нижнем регистре.
- Отключите Allow new users to sign up и Allow anonymous sign-ins. Для этих аккаунтов отправка писем не используется. Сброс забытого пароля выполняется администратором Supabase.
- Site URL — адрес опубликованного приложения. При переносе на другой Supabase проект обновите также `connect-src` в CSP внутри `index.html`.

Публичность кода не даёт доступа к базе: прямые права на таблицы отозваны у `anon` и `authenticated`, RLS включён, доступ возможен только через функции, проверяющие `auth.uid()` и участие в бюджете. Приглашение одноразовое, действует 7 дней, хранится в базе в виде хеша. Максимум два аккаунта в одном бюджете. У каждого аккаунта может быть один бюджет; устройства не ограничены. Для переноса аккаунта в другой бюджет нужна административная миграция.

## Модель расчёта

- Суммы представлены целыми копейками. Десятичный ввод разбирается точно; небезопасные итоговые суммы отклоняются.
- Начальный остаток относится к явно указанной дате. Дата в обзоре не меняет остаток незаметно: дата и баланс редактируются в настройках.
- Прогноз показывает дневные конечные остатки. Минимум включает начальный баланс, даже если доход того же дня устраняет дефицит. Число дней с дефицитом учитывает конечные остатки.
- Ежемесячные платежи 29–31 числа переносятся на последний день короткого месяца; исходный день восстанавливается в следующем. Дважды в месяц — 10 и 25 числа, начиная с даты операции.
- «Вся операция уже учтена» исключает все её повторения. Для оплаты отдельного повторения нужна отдельная запись.
- Переводы между собственными счетами не меняют суммарный баланс. Заём увеличивает средства, но не заработанный доход.
- Консервативный сценарий исключает доходы с пометкой «Ожидается».
- Кредитная модель использует равномерную месячную ставку и округление процентов до копеек. Комиссии, страховки, дневные банковские начисления и кредитные карты не моделируются.
- Долги в разделе сравнения — запланированные движения, а не подтверждённая текущая задолженность. Прогноз не учитывает неизвестные расходы.

## Структура

- `engine.js` — финансовая модель и нормализация данных.
- `app.js`, `index.html`, `style.css` — интерфейс, импорт и локальный бюджет.
- `cloud.js` — авторизация и REST-запросы Supabase.
- `sync-core.js` — объединение правок трёх версий.
- `sync-controller.js` — кеш, повторная отправка, конфликты и общий бюджет.
- `supabase/` — схема и тесты прав доступа; персональных данных в этих файлах нет.
- `scripts/check-public.cjs` — проверка на случайные секреты и личные экспорты перед публикацией.

Результаты аудита и границы проверок описаны в `AUDIT.md`.
